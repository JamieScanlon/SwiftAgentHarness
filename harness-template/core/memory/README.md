# Memory

Cross-session, durable knowledge: project-instruction files like `AGENTS.md` / `CLAUDE.md`, agent-written memory that survives session boundaries, layered scopes (user / project / team / local), and the read-time and write-time mechanics that keep memory useful instead of stale.

In-session compaction — condensing a single conversation's history — is its own top-level topic under [../context-engine/](../context-engine/). This area is about state that persists *across* sessions.

Memory sits in `core/` as the eighth inner-ring layer. It earns that placement because — unlike Tools, Skills, or MCP servers — it is the one persistent knowledge resource the [Context Engine](../context-engine/) auto-loads on every turn *without* the model invoking it. (Tools/Skills/MCP, by contrast, are model-invoked through the Tool System dispatcher; their registries are Tool System concerns.) Memory also has its own write side — consolidation, decay, scoring, recall sub-agents — that is too substantive to bury inside the Context Engine. See [../README.md](../README.md) for the full eight-layer ring.

## Open sub-topics (not yet drafted)

- **Skills as memory.** The skill-registry pattern (a separate, lazily-loaded library of agent capabilities) overlaps with memory in interesting ways: when does a memory get "promoted" into a skill, and how do the two surfaces stay coherent? The **Skill Workshop** plugin is a concrete answer: the agent observes its own runs, proposes new workspace `skills/` (pending-approval by default), runs them through a code scanner, refreshes the skill snapshot without restart. The memory→skill promotion path is "agent proposes a procedural memory; user approves or system-auto-approves in trusted workspaces; promoted memories become slash-invocable skills."
- **Memory-aware compaction integration.** Document the full handshake between in-session compaction and durable memory. The recommended approach is a **silent memory-flush turn before compaction**: a default-on pre-compaction step reminds the agent to dump important notes to `MEMORY.md` / `memory/YYYY-MM-DD.md` *before* the summarizer runs, so durable state has been promoted out of the conversation before any text gets summarized away. Plugin hooks (`before_compaction` and `after_compaction`) let memory plugins observe/annotate the cycle.
- **Cross-project memory transfer.** Today every harness keys agent memory by project path. Patterns for selectively promoting per-project insights to user-level (e.g., "I always prefer X" learned in one repo) are unexplored. A skill-precedence chain with explicit personal-vs-shared scopes is one model for this — but it's still keyed by location, not by topic-promotion logic.
- **Background memory consolidation pipeline.** The dreaming consolidation pattern is the most thorough treatment: three-phase pipeline (`light` ingests recent recall traces, `REM` extracts patterns/themes, `deep` ranks and promotes to `MEMORY.md`) with six weighted base signals (frequency 0.24, relevance 0.30, query diversity 0.15, recency 0.15, consolidation 0.10, conceptual richness 0.06) and phase-reinforcement boosts. `MEMORY.md` is the only durable promotion target; `DREAMS.md` is a human-readable diary; `memory/.dreams/` is machine state. Default cadence: nightly `0 3 * * *`. Reversible **grounded backfill** lane lets you replay historical daily notes through the deep ranker without polluting normal recall (`memory rem-backfill --rollback` / `--rollback-short-term`). 
- **Memory as an exclusive plugin slot.** Multiple memory backends can compete for a single active slot. A provenance-rich **Memory Wiki** layer can sit *beside* the active backend, adding claims, evidence, contradiction tracking, freshness scoring, and dedicated tools — without replacing the active memory plugin's recall, promotion, and dreaming responsibilities. The "active backend + parallel knowledge layer" split is worth borrowing.
- **Pre-reply blocking memory recall.** The **active-memory** pattern runs a bounded model call *before* the main reply, restricted to `memory_search` + `memory_get` tools, with a separate (typically faster, cheaper) model. Solves the "memory only fires when the model thinks to ask for it" problem by guaranteeing one bounded retrieval pass per turn. Scoped to direct chat types and per-agent allowlists by default.
